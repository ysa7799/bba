# BusinessOS — Engineering Operating Guide

BusinessOS is a multi-tenant Business Operating System SaaS (CRM, communications,
automation, scheduling, commerce, projects, helpdesk, marketing, AI) for Bahrain/GCC first,
then MENA and international markets. This file holds the permanent engineering rules. Read
`docs/ARCHITECTURE.md`, `docs/ROADMAP.md` and `docs/BUILD_PROGRESS.md` before starting work.

## Priorities (in order)

security → tenant isolation → correctness → data integrity → maintainability → testability →
UX → performance → development speed.

## Repository

- pnpm workspaces + Turborepo, TypeScript strict everywhere, ESM only.
- `apps/web` (Next.js UI only — no business logic), `apps/api` (Fastify HTTP layer),
  `apps/worker` (BullMQ job processors).
- `packages/*` hold shared infrastructure and domain services. Both `api` and `worker`
  import domain services from packages; routes stay thin.
- Internal packages are source-only TypeScript (`exports` → `src/*.ts`), compiled by the
  consuming app (tsup for api/worker, Next `transpilePackages` for web, Vitest for tests).
- Only create a package when real code needs it. No empty scaffolding.

## Commands

```bash
pnpm install
pnpm dev:deps            # start Postgres + Redis via docker compose (or use local services)
pnpm db:migrate          # apply migrations (uses MIGRATION_DATABASE_URL)
pnpm dev                 # run web + api + worker
pnpm check               # format:check + lint + typecheck + test (what CI runs)
pnpm test                # all unit + integration tests (needs Postgres + Redis)
pnpm --filter @businessos/api test
pnpm db:generate         # generate a migration after editing packages/database/src/schema
```

## Non-negotiable rules

### Tenancy

- `Organization` is the tenant. Every tenant-owned row has `organization_id NOT NULL` with a FK.
- Never trust an `organizationId` from the client as proof of access. Resolve access from the
  authenticated user → active membership → permissions (`requireOrgContext`).
- All tenant data access goes through `withTenant(ctx, tx => ...)`, which sets the Postgres
  RLS context (`app.org_id`). Repositories **also** filter by `organization_id` explicitly.
- `withSystem()` bypasses RLS and is reserved for auth, webhook routing, workers resolving a
  tenant, and platform admin. Every use must be justified in a comment.
- Tenant-scoped unique constraints include `organization_id`.
- Cross-tenant access is a CRITICAL defect: every new tenant resource gets an isolation test
  (read, list, search, update, delete, reference with a foreign ID).

### Auth & authorization

- Authentication = identity (sessions, tokens). Authorization = permissions. Keep separate.
- Permissions are checked server-side with `requirePermission('crm.contact.read')`.
  UI permission checks are convenience only.
- Never hardcode plan names (`plan === 'pro'`). Use entitlements (`hasEntitlement`, `getLimit`).
- Feature flags ≠ permissions ≠ entitlements.

### Data & money

- Money: integer minor units (`bigint`) + explicit ISO currency on every monetary record.
  Use `packages/shared/src/money.ts`. Never use JS floats for money. BHD has 3 decimals.
  Never silently convert currencies. Never default to USD.
- Timestamps: `timestamptz`, stored in UTC. Scheduling uses explicit IANA timezones.
- IDs: UUIDv7 generated by the app (`newId()`).
- All schema changes via Drizzle migrations. Destructive changes follow
  expand → migrate → switch → contract. Explicit `ON DELETE` on every FK.
- No unbounded queries: every list endpoint paginates (cursor or bounded limit).

### Input, errors, logging

- Validate all external input with Zod (params, query, body, webhooks, env, CSV, AI tool args).
- Never accept privileged fields from clients (user id, role, org id, totals, payment status).
  Use explicit allow-listed input schemas — no mass assignment.
- Throw `AppError` subclasses (`ValidationError`, `NotFoundError`, `ForbiddenError`, …).
  Never leak stack traces or internals in responses. Return 404 (not 403) for resources in
  another tenant.
- Structured logs (pino) with request IDs. Never log passwords, tokens, secrets, API keys,
  full card data. Use the redaction list in `packages/shared/src/logging.ts`.

### Payments & integrations

- Payment state only from server-side verification or authenticated webhooks — never from
  client redirects. Webhooks: verify signature, idempotent, dedupe, tolerate out-of-order.
- Provider-specific code lives only in its adapter (e.g. Tap). Domains use normalized types.
- No fake integrations: without credentials, ship interface + adapter + env schema + mock
  provider + tests, and mark the live connection `CONFIGURATION_REQUIRED`.
- Integration secrets are encrypted at rest and never sent to the browser.

### Async work

- Long-running work (email, messaging, imports, exports, workflows, webhooks delivery) runs in
  the worker. Jobs must be idempotent, retried with backoff, and visible when they fail.
- Domain events are written to the transactional outbox in the same transaction as the change.
  Domain events, audit logs, outbound webhooks and notifications are separate concerns.

### Frontend

- No business logic in UI. Every data view has loading, empty and error states.
- No UI for features without a working backend (hide or feature-flag instead).
- Strings go through the i18n layer; layouts must survive RTL (Arabic).

## Development loop (every phase)

Inspect → plan → implement only the current phase → validate (format, lint, typecheck,
tests, build) → security review (tenancy, authz, IDOR, mass assignment, validation, secrets)
→ fix → update `docs/ROADMAP.md`, `docs/BUILD_PROGRESS.md`, `docs/CHANGELOG_INTERNAL.md`
→ commit (`feat(scope): ...`) → continue. Never claim tests passed without running them.
Never disable a test to get green. Record non-trivial decisions in `docs/DECISIONS.md`.
